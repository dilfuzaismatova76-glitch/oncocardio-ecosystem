# Model Assignment Policy

## Status
Accepted (operational policy, not a clinical/architectural ADR — may
be revised without the same rigor as ADR-001..008, but changes should
still be logged here).

## Reference
ADR-000 (roles and workflow), CODEOWNERS, ADR-004 (rule classification).

## Purpose

Multiple LLM tools are used on this project (Claude, GPT, Gemini,
MAI-Code). This document is a **static lookup table**, not a running
process — routing decisions are made by the architect/lead (you)
reading this table, not by any AI deciding on another AI's behalf.
No tool in this project has authority over another tool's task queue
(see "Explicitly rejected pattern" below).

## Roles (unchanged from ADR-000)

- **Architect / Lead** — you. Owns all architectural and clinical
decisions. Writes or approves every `tasks/TASK-XXX.md`. Final
reviewer on all protected paths.
- **Implementation assistants** — Claude, GPT, Gemini, MAI-Code, or
any other tool used for code generation. All are peers in
authority: **none of them routes work to another, none of them
reviews another's output as a standing role.** Review is done by
the architect (optionally assisted by whichever assistant the
architect asks, on a one-off basis, not as a permanent function).

## Explicitly rejected pattern

Do **not** insert any assistant as a permanent "coordinator" that
writes prompts for other assistants, pre/post-reviews their output,
or decides task routing on its own initiative. This recreates, at the
process level, exactly the two-authority risk ADR-000 forbids at the
clinical-logic level: an extra, independent interpretation layer
between the architect's decision and the work actually produced,
which can drift from what the architect intended and is expensive to
reconcile. Every assistant receives its task directly from a
`tasks/TASK-XXX.md` file written or approved by the architect.

## Assignment table

| Task category | Assign to | Why |
|---|---|---|
| Category A/E rule *data* (thresholds, monitoring templates) | **Architect only** | Clinical content, not implementation — never generated by any assistant |
| Category B calculations (pure math, e.g. BSA, QTc formulas) | **Claude** | Small, precision-critical; errors are subtle (see BSA test bug found 2026-08-22) and expensive to catch after the fact; cheaper to have it correct on the first pass than to run a generate→review→fix cycle |
| Category C/D algorithm control flow (RiskModel, complex multi-criteria logic) | **Claude, with explicit ADR reference** | Protected path; structural correctness matters more than volume |
| `medicalcore/identity/`, `oncocardio/identity/` (matching/merge) | **Claude only** | Protected path (CODEOWNERS); patient-safety-critical |
| `*/rules/`, `*/risk/`, `*/alerts/`, `*/monitoring/`, `*/provenance/` | **Claude only** | Protected path (CODEOWNERS) |
| Pydantic/dataclass boilerplate from an already-frozen spec (domain entities, DTOs) | **Gemini / GPT / MAI-Code** | Pure transcription of an approved spec — low judgment required, high volume-to-value ratio for cheaper models |
| Repository/persistence CRUD for **non-protected** entities | **Gemini / GPT / MAI-Code** | Mechanical, pattern is fixed once (Repository[T] protocol + append-only convention), repeats per entity |
| Unit tests for boilerplate models (structural validation, enum rejection) | **Gemini / GPT / MAI-Code** | Repetitive, pattern-following |
| Unit tests for Category B math functions | **Claude generates, or Claude verifies reference values before merge** | See BSA incident: reference values are exactly the kind of detail cheaper models get subtly wrong and nobody catches by eye |
| UI scaffolding from an **approved wireframe/spec** | **Gemini / GPT / MAI-Code** | Once a wireframe exists and is architect-approved, layout code is mechanical |
| UI/UX layout decisions themselves (what a screen contains, adaptive field visibility logic) | **Architect (you) + Claude, on paper first** | This is a design decision, not implementation — no assistant invents UX unsupervised |
| Documentation, ADRs, domain-model docs | **Claude** | These *are* the architectural decisions in written form — same authority boundary as clinical logic |
| Refactors against an explicit, fully-specified rule | **Gemini / GPT / MAI-Code** | As long as the rule is unambiguous and doesn't touch protected paths |

## Review policy

- Boilerplate-tier output (Gemini/GPT/MAI-Code) is reviewed by the
  architect before merge — spot-checked for compliance with the
  originating `TASK-XXX.md`, not re-derived from first principles.
- Claude-tier output (math, protected paths, architecture docs) is
  still reviewed by the architect before merge, same as any other
  contributor — Claude's involvement does not bypass the CODEOWNERS
  gate.
- No assistant's output is merged solely on that assistant's own
  self-assessment ("tests pass" claims are verified by actually
  running them, not taken on faith — see BSA incident where a test
  file *looked* complete but contained wrong reference values).

## Prompt / task format (unchanged)

Every task handed to any implementation assistant uses the existing
`tasks/TASK-XXX.md` format: Reference (ADR/domain doc) / Scope / Out
of scope / Acceptance criteria. This is what makes an assistant's
output reviewable against a fixed contract regardless of which model
produced it.
